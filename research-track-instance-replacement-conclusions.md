# Итоги первого этапа: черновик

Черновик итогов первого этапа трека [«Смена экземпляра сетевой функции»](research-track-instance-replacement.md). Числа в квадратных скобках появятся после прогонов стенда. Остальные числа — расчёт модели на профилях нагрузки из раздела 6 трека.

## 1. Что сделано

- Поставлена задача: как срок смены экземпляра T влияет на обрывы запросов при замене контейнера сетевой функции (Envoy в Docker). Окно отвода Envoy при этом равно T.
- Построена аналитическая модель на основе M/G/∞. По распределению длительностей запросов и сроку T она даёт:
  - долю оборванных среди запросов, шедших в момент смены;
  - потерянную работу узлов;
  - среднюю потерю на один обрыв.
- Собраны три профиля нагрузки по открытым данным: REST API (Bermbach & Wittern), облачные функции (Shahrad et al., Azure), ответы LLM (BurstGPT).
- Создан стенд: два экземпляра Envoy, три узла сервиса, генератор пуассоновского потока, журнал по каждому запросу.
- Проведены калибровка и измерения по трём профилям при T = 10, 30, 60, 120 с, по 50 смен на точку, с 95%-ми доверительными интервалами (бутстреп по сменам).

## 2. Основные выводы

**Вывод 1. Модель подтверждена на стенде.** В [N из 15] точек предсказание модели попало в 95%-й интервал измерения. Расхождение не превысило [x процентных пунктов]. [Если где-то не попало — назвать точки и причину.] Совпали и вспомогательные величины: потеря на один обрыв и разброс числа обрывов между сменами (соответствует пуассоновскому). Итог: в проверенных условиях модель можно использовать для расчёта срока, не проводя опытов.

**Вывод 2. Долю обрывов определяет хвост распределения длительностей, а не средняя или медиана.**

- В момент смены в работе преимущественно оказываются длинные запросы (парадокс инспекции).
- У облачных функций медиана меньше секунды, а при T = 10 с обрывается около 59% идущих запросов.
- У REST при медиане 0,12 с все обрывы дают редкие запросы длиной в десятки секунд.

**Вывод 3. Значения по умолчанию не подходят для длинных запросов.**

| Срок | LLM | Облачные функции | REST |
|---|---|---|---|
| 10 с (Docker по умолчанию) | ≈ 54% | ≈ 59% | ≈ 1% |
| 30 с (Kubernetes по умолчанию) | ≈ 22% | ≈ 35% | меньше 1% |

**Вывод 4. Срок нужно выбирать по допустимой доле обрывов и распределению своего сервиса.** Универсального значения нет. Расчёт модели (REST — с типичной долей долгих запросов 0,004%):

| Допустимая доля | REST | Облачные функции | LLM |
|---|---|---|---|
| 10% | < 1 с | 91 с | 54 с |
| 1% | 21 с | 177 с | 131 с |
| 0,1% | 52 с | 212 с | 181 с |

**Вывод 5. Правила вида «T = p99» дают очень разную долю обрывов** в зависимости от хвоста [числа — из таблицы раздела 1 трека]. Значит, такие правила не гарантируют заданного качества.

**Вывод 6. Увеличение срока имеет предел.**

- Обрывов становится меньше, но каждый оставшийся обходится дороже. У LLM потеря на обрыв растёт с ≈ 36 с генерации при T = 10 с до ≈ 145 с при T = 120 с.
- Старый экземпляр живёт до T, поэтому смена со сроком в несколько минут длится несколько минут.
- Для малых долей обрывов (0,1%) нужный срок приближается к самым долгим запросам. Дальше помогают не секунды, а другие средства: возобновляемые потоки, повторы, стратегия отвода (второй этап).

**Вывод 7, для REST.** Если долгий запрос и так обрывается своим тайм-аутом D раньше срока смены (D ≤ T), смена обрывов не добавляет. Согласовать тайм-аут запросов со сроком смены важнее, чем увеличивать срок.

## 3. Методика выбора срока (практический результат)

1. Собрать распределение длительностей запросов своего сервиса по журналам, обязательно вместе с редкими долгими запросами.
2. Задать допустимую долю обрывов или допустимую потерянную работу за смену.
3. Рассчитать срок T моделью.
4. Согласовать с этим сроком тайм-аут остановки Docker и окно отвода сетевой функции.

## 4. Ограничения

**Среда измерений:**

- Измерения проведены на одном персональном компьютере (Windows, Docker Desktop: контейнеры работают в виртуальной машине). Другие процессы могли конкурировать за процессор и память. [Если итоговые прогоны будут на Ubuntu с Docker Engine — указать это.]
- Все компоненты работают на одном хосте. Реальной сети между клиентами, балансировщиком и узлами нет: нет сетевых задержек, потерь пакетов и разницы между машинами.
- Узлы сервиса имитируют работу ожиданием: реальной нагрузки на процессор или GPU нет.
- Нагрузка синтетическая: генератор воспроизводит распределение, а не реальные запросы.

**Допущения модели:**

- Обслуживание без очереди: у узлов достаточно мощности, запросы не ждут свободного обработчика.
- Клиенты не повторяют оборванные запросы.
- Поток запросов пуассоновский и стационарный: нет пачек и суточных колебаний.
- Длительности запросов независимы друг от друга.
- Рассматривается одна смена одного экземпляра, а не поэтапное обновление многих экземпляров подряд.
- Стратегия отвода одна: все соединения отводятся сразу (immediate).
- Окно отвода равно сроку принудительной остановки.
- Узел прекращает работу, когда клиент ушёл. Если узел дорабатывает запрос, потерянная работа будет другой.

**Объект и протокол:**

- Проверен только Envoy и его механизм отвода. Другие сетевые функции (NGINX, HAProxy) не проверялись.
- Среда управления контейнерами — только Docker, без Kubernetes.
- Протокол — HTTP/2 без TLS. Долгоживущие соединения без границ запросов (WebSocket) не рассматриваются.

**Входные данные:**

- Профили построены по открытым данным разных лет и источников и описывают типичную услугу, а не конкретный сервис.
- Для облачных функций разброс длительностей взят между функциями, а не между вызовами одной функции.
- Долгие запросы REST оценены по 10 случаям. На стенде их доля увеличена до 0,1% (в данных около 0,004%), чтобы набрать статистику.
- Результаты для малых долей обрывов зависят от выбранного усечения распределения: самые долгие запросы в данных редки и плохо измерены.

**Стенд и статистика:**

- Фактический срок обрыва на ≈ 0,2 с больше заданного, Envoy принимает только целые секунды. Модель сравнивалась при фактическом сроке.
- Поток ответа LLM имитируется частями раз в 250 мс, а не по токенам.
- Доверительные интервалы учитывают только случайный разброс между сменами. Систематические погрешности стенда выявляет только калибровка.

**Метрика:**

- Доля оборванных и потерянная работа не равны качеству для пользователя. Как обрыв воспринимает пользователь, зависит от повторов и интерфейса, а это второй этап.

- Пачечный поток запросов.
- Проверка на отдельном сервере с Ubuntu и Docker Engine, а затем на нескольких машинах.
